# 迷宫主入口被侵略子系统同名函数遮蔽：考古报告（issue #103）

> 状态：只读研究，未改动 `target/`、`ere/`、`yml/`、`test/`、`tools/`。
> 方法：逐段精读两份实现（`target/ERB/迷宮/DUNGEON.ERB` 1091 行、`target/ERB/侵略/AGENT/AGENT.ERB` 1058 行）＋全库调用点检索＋补丁 README 断代（Shift-JIS/UTF-8 转码后全文阅读）＋行级 LCS diff。行号均为 1-based。

## 结论（先行）

1. **判定：复制粘贴事故，不是有意复用。** `侵略/AGENT/AGENT.ERB` 是 `迷宮/DUNGEON.ERB` 在 **2015-06-24 之前**某时刻的旧快照拷贝（其独有的旧逻辑恰好缺失 2015 年三轮补丁的全部特征，见 §2.3），此后上游补丁只打在 DUNGEON.ERB 上。由于 Emuera「首个加载生效」＋目录遍历序（`侵略` 先于 `迷宮`，issue #12 实测），**实际运行的是旧快照**，2015 年之后上游对迷宫主入口的全部改进（勇者资产经济、目标阶层 AI、体力续探、战报阶层显示）在原作里从未生效。
2. 作者本人知道这组撞名并做过**部分修复**：AGENT.ERB 里用 `[SKIPSTART]/[SKIPEND]`（AGENT.ERB:880/1020，语义见 `.factory/skills/emuera-basic-agent-guide/references/csv-reference/erb-format.md:50-59`）禁用了自己的旧版 `@CHECK_STATUS`，让 DUNGEON.ERB 的新版生效——但漏掉了同文件的 `@DUNGEON` 与 `@GET_JUNK_ITEM`。这半吊子修复本身就是「事故而非设计」的最强旁证：没人会有意让一个入口函数被遮蔽、却精心修复它的辅助函数。
3. **移植以 `迷宮/DUNGEON.ERB` 为准**（作者意图版本），AGENT.ERB 的 `@DUNGEON` 登记为缺陷死代码（参照 #14 口上 902/903 的处置）；`@GET_JUNK_ITEM` 两份逐字节相同（34 行 0 差异，实测），任留其一即可；CAMPAIGN_EVENT 的 12 个函数同样以 CAMPAIGN_EVENT.ERB 版为准（AGENT_EVENT 是一次**未完成的复制改名尝试**，其配套的 AGENT_1.ERB 全部 14 个函数无任何调用点，入口菜单项也被注释掉）。

一个对任务背景的重要修正：**「DUNGEON.ERB 版整体被拒」不准确**。DUNGEON.ERB 有 4 个函数（DUNGEON.ERB:3/856/1041/1076），其中 `@CHECK_STATUS`（AGENT 版被 SKIP，不参与仲裁）与 `@GET_DOWN_ENEMY`（AGENT.ERB 无此函数）**实际生效**；被遮蔽的只有 `@DUNGEON` 与 `@GET_JUNK_ITEM` 两个。

## 二、判定：有意复用还是复制粘贴事故

### 2.1 全库调用点：`@DUNGEON` 只有一个调用方，且不属于任何一个子系统目录

全库检索 `CALL/JUMP/CALLFORM/TRYCALL/TRYJUMP/JUMPFORM … DUNGEON`（词边界，排除 `DUNGEON_ROOM` 等长名；其余 `"DUNGEON"` 字符串命中均为卖淫系统的场所标签参数，如 DUNGEON_BITCH.ERB:12）：

| 调用点                                                  | 上下文                                                                                         | 实际执行           | 期望 |
| ------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------ | ---- |
| `SYSTEM/SYSTEM ver1.0.3.ERB:271` `CALL DUNGEON, LEADER` | `@EVENTTURNEND` 日循环：`SIF CFLAG:LEADER:1 == 12`（**战役派遣中的奴隶**， invading 事件迷宫） | AGENT 版（旧快照） | 见下 |
| `SYSTEM ver1.0.3.ERB:290` `CALL DUNGEON, LEADER`        | 日循环：`(CFLAG:A:1 == 2 \|\| 3) && FLAG:502 == 0`（**攻略中勇者 / 迎击中奴隶**，普通地下城）  | AGENT 版（旧快照） | 见下 |

调用方是系统层日循环，与「迷宮」「侵略」两个目录都不存在从属关系；`@DUNGEON` 是**全局唯一的迷宫日循环入口**，两个子系统目录里的同名定义是两份完整实现互相顶替，而非「各自 subsystem 内部各自的 DUNGEON」（否则调用方应分属各自子系统）。这不是「有意复用」的形态——有意复用只需要一份定义。

### 2.2 参数与副作用兼容性：不兼容，且伤及第三方调用点

- `@DUNGEON` 签名相同（单参），**但副作用不兼容**：DUNGEON 版的陷落结算走 `CFLAG:580`（勇者持有金）经济体系——该体系由 `ENTER_ENEMY.ERB:133`（勇者登场初始金，:107-133，注释 `;Ref DUNGEON_TOWN.ERB`）、`DUNGEON_TOWN.ERB`（街上结算/借贷/担保人，:121/:207/:281/:300 等）、`DUNGEON_ROOM.ERB`（购物/住宿扣 580，:201-321）、`DUNGEON_TRAP.ERB`、`DUNGEON_BITCH.ERB`（卖淫收入进 580）、`DUNGEON_QUEST.ERB:37`、`CHARA_TEMPTATION.ERB:192/321/341`、`USE_EX_ITEM.ERB:120`、`CHARA_INFO ver1.0.1.ERB:456-543`（所持金显示）、`LOOK.ERB:1581-1587`，以及魔改新增的 `魔改新增/诈骗陷阱.ERB`（骗取勇者现金，:35-230）、`魔改新增/處刑改寫.ERB:337-341`（处刑「消除记忆释放」掏空 580）共同构成闭环（语义见 `資料_非必要無須解壓/eramaouフラグまとめ.txt:456-459`：580=所持金、581=换金前金品、582=借金）。AGENT 版的 `100×等级` 赏金与这一切不联动：勇者被捕获时魔王拿到的钱与勇者实际身家无关，且 `CFLAG:580` 不经陷落结算清零（DUNGEON 版 `@GET_DOWN_ENEMY` 才做 `CFLAG:580 = 0`，DUNGEON.ERB:1087）。**魔改新增的两个功能直接围绕 580 设计却顶着旧版主入口运行**，是「运行配置与设计意图脱节」的直接证据。
- `@CHECK_STATUS` 的第三方调用点 `迷宮/DUNGEON_RYOUZYOKU.ERB:2940` `CALL CHECK_STATUS, ARG, 1` 显式传入 `MODE=1`（静默模式）——**该参数只在 DUNGEON.ERB 版签名（`, ARG:0, MODE = 0`，:856）中有意义**。此调用点只有在 DUNGEON.ERB 版生效时才能得到期望行为；AGENT 版正是为此被 `[SKIPSTART]` 禁用的（否则旧版无条件打印、且无 `STATUS:7` 加权总分返回）。这是「参数只在某一份里有意义」的强证据，也证明作者做过定向修复。
- 运行时形成**混合体**：生效的 AGENT 版 `@DUNGEON` 在 :663 `CALL CHECK_STATUS,ARG:0`，实际解析到 DUNGEON.ERB:856 的新版（AGENT 版已 SKIP、不参与同名仲裁）。旧主循环驱动新辅助函数，跨文件拼装——任何「有意复用」的设计都不会长这样。

推断链（标注：以下为推断，依据如上表实测）：AGENT.ERB 的 `@DUNGEON` 主体复制于 **2014-05-15 之后、2015-06-24 之前**的 DUNGEON.ERB；其 `@GET_JUNK_ITEM` 却是 **2016-06-05 之后**的版本。即 AGENT.ERB 不是一次性快照，而是「旧主体＋后被同步刷入的新函数」——最合理的解释是 osaihu 这类「整函数替换」补丁在应用时被无差别刷进了全库两份同名函数（对被遮蔽的那份而言是无效劳动），而非有人有意维护两份。加上 `;@CALLME雄霸天` 标记（全库仅这两处，AGENT.ERB:2 / DUNGEON.ERB:2，同一经手人）与 `[SKIPSTART]` 半修复（§1.3），整体图景是：**经手人复制 DUNGEON.ERB 到侵略/AGENT/ 下做「特工/扰乱」方向的改造（AGENT_1.ERB、AGENT_EVENT.ERB 同期产物，见 §4），主入口改完入口名（AGENT_MENU）却把 @DUNGEON 原样留在文件里，事后意识到撞名、修了 CHECK_STATUS、漏了 DUNGEON 与 GET_JUNK_ITEM**。

### 2.4 判定

**复制粘贴事故。** 四条独立证据链交汇：(a) 唯一调用方在系统层，两份实现是完整顶替关系而非分工；(b) 副作用不兼容且伤及 580 经济体系与魔改新增功能；(c) 补丁史 2013-2016+ 只认 DUNGEON.ERB，AGENT.ERB 独有特征恰是 2015-06 前旧貌；(d) 作者对撞名做过半途修复（SKIP 掉 AGENT 版 CHECK_STATUS 让新版生效），却留下主入口被顶——没有理性设计会长这样。

### 4.1 结构关系

- `侵略/CAMPAIGN/CAMPAIGN_EVENT.ERB`（319 行）与 `侵略/AGENT/AGENT_EVENT.ERB`（307 行）同源：13 个差异块之外逐行相同。CAMPAIGN_EVENT 定义 13 个函数（:6 `@CAMPAIGN_MENU` ＋ 12 个共享函数），AGENT_EVENT 定义 13 个（:6 `@AGENT_MENU` ＋ 同名 12 个：`SELECT_CAMPAIGN`(:127)、`CAMPAIGN_ROOM`(:152)、`CAMPAIGN_ROOM_EXTRA`(:166)、`CAMPAIGN_QUEST`(:179)、`CAMPAIGN_TRAP`(:201)、`CAMPAIGN_EQUIP_SELECT`(:213)、`CAMPAIGN_MONSTER_LIST`(:224)、`CAMPAIGN_MONSTER_EXTRA`(:236)、`CAMPAIGN_DUNGEON_LV`(:248)、`CAMPAIGN_GAMEOVER`(:258)、`CAMPAIGN_EXP_PILLORY`(:279)、`CAMPAIGN_ENDING`(:298)）——**被遮蔽的正是这 12 个**（菜单函数因改名而不冲突）。

### 4.3 判定与移植安排

**同一种事故，且比 @DUNGEON 那组更明确是「半途而废的复制改名」。** 依据链：(a) AGENT_1.ERB 归一前缀后与 CAMPAIGN_1.ERB 完全相同且全部函数无调用点——改名复制做了数据层、没做分发层；(b) AGENT_EVENT 的 12 个共享函数相对 CAMPAIGN_EVENT 是**功能缺失**（丢 PARTY_DEL、丢魔改赤森适配）而非演进，且文案是繁体（魔改/后期经手人笔迹）而 CAMPAIGN_EVENT 是简体（汉化底本），缺失方向与「旧版」矛盾、与「从某版本复制后删改」吻合；(c) INVASION.ERB:84 把 AGENT 入口菜单项注释掉——启用后又回退的痕迹。

**CAMPAIGN_EVENT 不是死代码、AGENT_EVENT 也不是它的新版**：CAMPAIGN_EVENT 的 `@CAMPAIGN_MENU` 仍在生效（INVASION.ERB:98 玩家可见入口 [9]），只是它依赖的 12 个下游分发函数被 AGENT_EVENT 顶掉，运行时是「CAMPAIGN 菜单（新）＋ AGENT 分发层（旧）」的又一个混合体（例如玩家从 [9] 进菜单、选招带赤森开关，但战役失败/完结时不解散队伍——PARTY_DEL 缺失）。

移植安排建议：

1. 12 个共享函数以 **CAMPAIGN_EVENT.ERB 版为准**（含 PARTY_DEL 清理），AGENT_EVENT 版登记为缺陷死代码；差异四处记入缺陷登记（GAMEOVER/ENDING 不解散队伍、QUEST 少 FORCEWAIT 为可感差异）。
2. `@CAMPAIGN_MENU` 以 CAMPAIGN_EVENT 版为准（含人数上限与赤森奴隶开关——后者要连着 `魔改使用.ERH` 与 `CHAR_MAKE.ERB` 一并排期）；`@AGENT_MENU` 与 `AGENT_1.ERB`、`AGENT.ERB` 一样归入「事故残留清单」，侵略子系统阶段不排期、只登记。
3. `@CAMPAIGN_MONSTER_EXTRA` 分发器两版皆无调用点（全库检索仅定义处），属上游自带的死代码，登记但不影响排期。
