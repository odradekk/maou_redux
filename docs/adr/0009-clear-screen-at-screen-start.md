# 每一屏开始前整屏清空，不保留历史

决策与实测数据见 #720；换屏入口与夹具的未读输出检查在 #721 交付，页面接入在后续工单。

## 问题

游戏几乎从不整屏清空，画面历史只增不减，而引擎每处理一次输入的耗时都和历史行数成正比：渲染层每次输入都把全部历史行重新渲染 2～3 次，并为滚到底部做一次全页重排。实测（真实引擎，从新游戏进入调教，每条指令输入 4 次）：历史 169 行时单次输入约 55 ms，约 5,050 行时 3.2～5 秒。玩家反馈「一个指令得等好几秒」，游戏侧计算只占几十毫秒，瓶颈全在历史渲染。

引擎自带的行数上限救不了它：截断代码读的是错误的配置路径（读 `system.disableClear`，同一文件其他地方都读 `config.…`），永远不执行；而且它本来也只在关闭清屏指令时起作用。所以只能由游戏自己清屏。

## 决定

不再保留历史：**每一屏开始绘制前整屏清空**（无参 `era.clear()`），画面上永远只有最新的一屏。

- **一屏**指从玩家一次菜单选择开始，到下一次需要玩家做菜单选择为止的全部输出。菜单选择后的结算、口上逐行等键都留在同一屏里累积，玩家照常逐行读完；回到菜单（调教指令菜单、主菜单、各子页面的列表）时先整屏清空，再画新的一屏。
- **换屏**走统一入口（`ere/page/components/screen-change.js` 的 `change_screen`），各页面在每一屏开始时调用它，不各自散写清屏代码。
- 不在每次按键时清屏：口上逐行显示会变成一句一屏；且引擎在右键快进时遇到清屏会强制停下并退出快进，每次按键都清屏会让快进完全不能用。

## 未读输出

换屏之前，上一次菜单选择之后产生的输出必须已经被玩家按键确认过——任何结果在被清掉之前都要玩家按过键。

不能在换屏入口里无条件 `waitAnyKey` 来保证这一点：引擎按「上次输入之后有没有新输出」决定等不等，而菜单输入的回显本身就算一次输出，这样每次菜单选择后都多一次按键。缺等键的路径在那段输出的末尾补等键；测试夹具在整屏清空时检查被清掉的行里有没有「上一次输入之后打印、且不是输入回显」的行（`unread_output_clears` 记录），端到端测试断言这份记录为空。

## 与 ADR-0003 的关系

本决定取代 ADR-0003 的「重绘 = `clear(自己的行数)` + 重画」：就地重绘的行号基准点不再需要，画面组件改为「换屏 + 绘制」，基准点逻辑没有剩余调用方后删除。ADR-0003 的「重绘只发生在玩家交互之后」约束保持不变——新规则正是它的推广：清屏只发生在玩家交互之后（一屏的开始），叙述流中间不清屏。ADR-0003 的其余部分（行数靠运行时测量、Row 语义、快进遇 clear 停下）不受影响。

## 边界

- **屏内局部清除不动**：存读档、设施、通信、结局、角色定制等页面的 `clear(n)` 局部清除，以及只清输入回显的 `clear(1)`，都发生在一屏之内，保留；它们清的行数只允许针对本屏内容，不依赖本屏开始之前的行。
- **右键快进**：引擎在快进态遇到 clear 会强制等一次按键并退出快进。按新规则，快进在每一屏开始时停一次，是有意的「翻页」行为。
- 玩家不能回看旧内容，换来稳定的反应速度；游戏不提供历史回看功能。
- 不涉及存档结构，不改版本号。
