# 移植期不保证存档兼容：破坏性改动即废档，不写迁移代码

引擎给了两道闸门（`dev-guides/11-saves.md`）：存档的 `code` 与【游戏标识】不符即拒读，存档的 `version` 低于【最低支持版本】即拒读。#2 据此定了临时规则「破坏性改动时【版本】与【最低支持版本】一同抬升」，但**没有定义什么算破坏性改动**，规则因此从未被执行过。

写迁移代码这条路在这个引擎上走不通，理由不是工作量，是**缺输入**：

| 事实                                                                                 | 出处                                           |
| ------------------------------------------------------------------------------------ | ---------------------------------------------- |
| Emuera 有内建只读变量 `LASTLOAD_VERSION`（上次加载的存档版本号），原作用它做版本判断 | `target/ERB/SYSTEM/SYSTEM_DATA.ERB:339` `:448` |
| EraElectron 的 `global:version` **恒等于 GameBase 的版本**，不是被读入那个存档的版本 | `dev-guides/09-static.md:598`                  |
| 未声明的变量序号能静默写入并进存档，旧档里带着无人认领的键                           | #13                                            |

也就是说：**读进来那个存档是哪一版，游戏代码根本拿不到。** 迁移代码没有可靠判据知道该补什么。

因此：**移植期不保证存档兼容。破坏性改动时同抬【版本】与【最低支持版本】，引擎直接拒收旧档，不写任何迁移代码。**

## 什么算破坏性改动

判据一句话：**同一条寻址，在旧档里读出的值是否仍然是它现在的语义**——否则即破坏性。

| 改动类型                                    | 旧档读出什么                                | 破坏性 |
| ------------------------------------------- | ------------------------------------------- | ------ |
| 普通表新增序号                              | 引擎为新增系统变量表的变量赋 0              | 否     |
| 新增整张静态表                              | 引擎创建存档中不存在的数据表                | 否     |
| 新增普通角色变量表                          | 引擎为所有角色创建子表并初始化              | 否     |
| 扩展角色表（`extendedCharaTables`）新增字段 | `fillData` 死分支，不补齐，读出 `undefined` | **是** |
| 改变已有序号的语义、量纲或单位              | 旧值原样返回，含义已变                      | **是** |
| 删除或重排序号                              | 旧值挂在错误的地址上                        | **是** |
| 角色预设内容变更                            | 该角色带旧预设值，无人补正                  | **是** |

前三行判「否」的依据是引擎 `loadData` 自己会补 0，而 0 就是新字段的正确初值。第四行的死分支见 #13 与 `test/portcflag-table.test.js`。

## 版本号另起 `0.0.0` 轴

原作版本号 `93106` 不再沿用——移植版的进度与原作版本无关，继续沿用会让「抬版本」这个动作同时意味着两件事。

| 字段             | 类型   | 取值                                 |
| ---------------- | ------ | ------------------------------------ |
| 【版本代号】     | String | `"0.0.0"`；移植完成时为 `0.1.0`      |
| 【版本】         | Number | `major×1000000 + minor×1000 + patch` |
| 【最低支持版本】 | Number | 恒等于【版本】                       |
| 【游戏标识】     | Number | `931060`，**冻结**                   |

【游戏标识】的命名理由（#2：原版本号加一位后缀）已随版本轴改动失效，但取值必须冻结——它是存档归属校验的依据，且与 `sav/global.sav` 不一致时引擎**拒绝启动并报错**。

抬升由**实施票自己做**，触发条件是上表判据，不是每票无条件递增。

## 不加机器守卫

判据主体不可机器化——机器看不出「语义变没变」。唯一可机器化的子集是「扩展角色表字段数变了但版本没抬」，覆盖面太窄。

代价那一侧是明确的：`docs/agents/ticket-sop.md` §2 列出的四处固定冲突面（`LEDGER_COUNT_BASELINE`、`test/engine-skip-baseline.txt`、`tools/mutations/*.mjs`、`docs/stub-registry.md`）每加一处，所有并行票都要多付一次 rebase 成本（实测约 15 分钟）。改为在 SOP §5 增加一条人工检查判据。

## 后果

**自动存档占 99 号槽，这是对原作的有意偏离。** 原作全库只有一处玩家存档写点（`SYSTEM_DATA.ERB:185`，槽位 0–98），99 号槽在读档界面被渲染却**没有任何写点**，是未实现的遗留空位；原作也没有定义 Emuera 的内建自动存档钩子 `@SYSTEM_AUTOSAVE`。占用它不改变任何原作可见行为。自动档同样盖着【版本】，因此**不降低实机验收成本**——那件事仍按 SOP §6 的临时改代码置位解决。

**`PORT_DATA_VERSION` 失去迁移消费者。** #67 给它定的用途是「迁移代码据此比对存档里的值 < 该角色应有版本决定补值」，与本决议冲突；判据把「角色预设内容变更」划为破坏性之后，它降格为诊断戳——读档后可辨别该角色由哪一版预设生成。曾考虑给「不写迁移」开一个角色预设级的例外，未取：口子一开就要再判一条「哪些算角色预设级」的边界，判错的后果是玩家拿着半迁移的档，比干脆废档更坏，且这类缺陷在夹具里看不出来。

**原作的历史迁移代码不移植。** `target/ERB/其他/DATA_FIX.ERB`（107 行，由 `@EVENTLOAD` 无条件调用，无版本判定）修的全是 Emuera 旧档的具体缺陷。这不是本决议的新裁定，而是 #1 已将「读取 Emuera 旧存档」判为出界的直接推论。其中三处对新档仍有语义的行（`EX_TALENT:MASTER:200 = 1`、`MAXBASE:A:0` 下限 600、`MAXBASE:A:1` 下限 100）逐条判定归属后另行安置。
