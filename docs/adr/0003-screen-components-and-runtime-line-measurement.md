# 表现层用画面组件，行数靠运行时测量

引擎的界面能力比 Emuera 高得多——Vue + Element Plus 的 24 列可嵌套网格，文本支持逐 span 的颜色/字号/字重/悬浮提示/超链接，另有进度条、折线图、图片、背景遮罩、吐司通知。但形状是死的：**屏幕仍是一条追加式的 Row 流，没有 HTML 逃生舱、没有自定义组件、API 清单里也没有常驻面板**。非追加手段只有 `clear(n)`、`replaceText`、`replaceInColRows`。

所以「精细优化表现」的实际含义是**重绘纪律 + 网格排版 + 行内富文本**，不是组件树。

因此：**表现层由画面组件构成，每个组件知道自己占几行**；行数取绘制前后 `getLineCount()` 的差值，**不静态声明**；重绘 = `clear(自己的行数)` + 重画。

## 为什么运行时测量而不是静态声明

`clear(n)` 的单位是 Row，`getLineCount()` 数的也是 Row，两者严格同单位，且 `clear` **返回清屏后的行数**可直接自校验（`dev-guides/06-output.md`）。静态声明在内容可变的组件上必然出错——角色列表的行数随人数变，而人数是玩家行为的函数。

## 为什么不是声明式页面树

引擎没有 diff 渲染。声明式树最终还是要有人算出该 `clear` 几行，抽象没有消掉那个计算，只是把它藏起来了。而薄封装（只把 `print` 系语义化）挡不住排版散落——现有页面已经各自发明了菜单按钮与状态条的排版助手，薄封装只是把重复挪个位置。

## 重绘只发生在玩家交互之后

手册写明：**右键快进显示时遇到 `era.clear` 会在清屏前停下**（`dev-guides/06-output.md`）。在叙述流中间重绘的组件会反复打断玩家快进。这是约定的一部分，不是可以事后发现的东西。

## 美术资源分期进场

原作有 272 张图与 3 首 BGM，当前 `resource: false`、`res/` 为空。**UI 图标与 BGM 随本层一起进场**——组件必须知道自己能不能用图，这条不定，网格约定就是建在假设上的。内容图（怪物立绘等）后置，纯搬运、无设计风险。

## 后果

夹具原本把一次 `printMultiColumns` 的 N 格记成 N 条 `lines`（对 #48 的输出比对来说是对的：比对关心「输出了什么」而不是「怎么排」），而引擎把整次调用记成**一个 Row**（`dev-guides/08-ui.md`：「输出的内容在编程上属于同一行（Row），`await era.clear(1)` 会将它们同时清除」）。

于是同一段代码在两边得到不同的行数：4 格 `printMultiColumns` 后，夹具的 `getLineCount()` 增量是 4，引擎是 1。组件记下增量 4、稍后 `clear(4)`，**在引擎里会连带抹掉它上面三行无关内容**。

这是「测试全绿、在引擎里才红」的第四例，且只要 UI 套件建在当前夹具上就**必然会发生**。修法按 `docs/skeleton.md` 的通则，把查明的引擎行为补进注入点：给每条 `lines` 条目加 `row` 字段，`getLineCount()` 返回不同 row 数，`clear(n)` 按 row 删除；归一化器继续遍历条目、不看 row，因此 #48 不受影响。**这一步是画面组件的前置条件。**
