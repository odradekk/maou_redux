# T18 输出比对工具链（issue #48，验证决策 #9）

输出比对工具将 ere 回放结果和 Emuera 基准日志转换为同一格式的事件流，再逐条比较并记录差异原因。最初的调教样本为 `target/emuera.log`，后续样本登记在 `tools/compare/samples.js`。工具位于 `tools/compare/`，离线运行，无第三方依赖：

| --------------- | -------------------------------------------------------------------------------------------------------------- |
| `normalize.js`  | 两侧原始输出 → 事件流（text / input / menu / gauge / lossbar / calc / image；装饰行丢弃）                      |
| `diff.js`       | menu/gauge 集合比对 + 其余条目 LCS 对齐；差异经 rules 归因成 version / stub / unexplained                      |
| `rules.js`      | 差异归因规则清单，每条注明理由（范围 B 规则组受 `scope` 条件限制，#161）                                       |

| `assertions.js` | 日志算式行 → 变量层断言（含自校验与链一致性）                                                                  |
| `replay.js`     | ere 侧回放器（调教段）：#16 测试夹具 + 温妮初始状态设置 + 真实 `run_train` 驱动                                |

## 覆盖范围与限制

**调教段**：旧样本 `target/emuera.log` 只覆盖调教流程中的一段，比对结果不能代表其他流程。样本来自环形缓冲的最后 5000 行，不含标题、商店、迷宫和日循环；录制版本也早于 `target/` 的版本（#9 勘误一、二）。

**范围 B（#161 起）**：`golden/` 的六份样本覆盖三个流程：标题→读档→据点主菜单，存读档界面（命名、保存、覆盖、读取），以及日循环（休息两次推进一日）。每个流程记录两份：直接使用 save99 的状态（`natural`），以及按录制清单设置变量、显示更多条件按钮和面板的状态（`max`）。逐份运行 `node tools/compare/cli.js --sample <名>`，四项统计基线由 `test/compare-scope-b.test.js` 检查。通过表示这些样本中的输出匹配，或差异能按 `rules.js` 的范围 B 规则解释。

**出售样本（#338 起）**：`golden/sale-natural.log` 记录 `natural` 状态下的能力提升入口、出售确认、成熟奴隶市场选择及黑市后续流程。回放由 `replay-b.js` 驱动，独立基线位于 `test/compare-scope-b.test.js`。

**尚无样本的流程不能声称通过输出比对。** 迷宫、战斗、口上及其他调教流程按 #109 第六项结论使用单元测试和引擎运行验收；要增加输出比对，须先录制样本并补充差异规则。范围 B 内也有无法直接比较的项目，例如复用编号造成的配对差异，以及引擎的按钮和清行方式不同。这些差异仍会记录，只是按规则分类，详见 `rules.js` 的范围 B 注释。

## 三项设计决策（#48）

### 1. 比对起点：手工设置等价角色初始状态，不解析 save00.sav

依据：

- 首回合的全部初始值**可从日志自身推导**。PALAM 初值 = 算式行 from 侧
  （`阴核 5240+300=5540`）；BASE 初值 = 回合后状态条 + 损耗回推
  （(1445/2000) + `-5`）；ABL / 素质 / 刻印 / CFLAG 由源一览与换算结果反解
  （`tools/compare/replay.js` 的初始值表逐条注明证据行；推导表见文末）。
  8 条算式断言在回放的 before/after 两端均通过（`test/compare-first-turn.test.js`），
  验证了这些初始值与日志中的计算结果一致。
- `save00.sav` 与日志记录区间的**时间对齐关系不可知**：日志是同场次的最后
  5000 行，存档是同场次的某一时刻——解析它得到的不是「记录区间起点」。
- 二进制格式解析是独立工作量，解析器缺陷可能产生与游戏实现无关的差异，
  #9 原型的静默截断缺陷就是这类。初始状态设置复用测试夹具的既有机制，不增加采集范围。

### 2. 录制器：复用 #16 夹具，不另造 print 代理

#9 曾计划增加 print 代理和测试模式开关。#16 的夹具已能加载真实 SDK 并替换输出函数，游戏代码无需修改，因此直接复用。#48 补充了 `printMultiColumns`、`printInColRows`、`printImage` 的逐格记录，保留既有测试行为。输入由回放器单独包装 `era.input`，将输入标记加入 `lines`；不将这项职责加入输出夹具。

### 3. LCS 粒度与装饰行的判定

- **粒度**：一「格」一条目。菜单行拆成 (标签, 编号) 条目、参数条网格拆成
  (键, 数值) 条目、算式行拆成数值四元组；text / input / calc / lossbar 走
  LCS（叙事次序是行为的一部分），menu / gauge 走集合比对（画面布局无次序
  语义，集合化就是「容忍排版差异」的实现；检验 2 重跑通过）。
- **装饰行**：空行 / 分割线 / 省略号整体丢弃。本分类器实测 5000 行样本：
  空行 260 + 分割线 462 + 省略号 364 = 1086 行（**21.7%**；#9 原先统计为 21.2%，
  差额是本分类器把 palam_up 的 31 字符短分隔线也计入 divider）。量级与
  结论不变：比对它们只产生噪音。

## 补充设计结论：结构化进度条记录 → gauge（#74，让表现层可替换而不破坏比对）

ere 侧的 gauge 来源自此分两路：

- **文本记录仍走 `classify_line`**（与黄金样本同一套分类器）。它不能随
  #74 删除：损耗条（`体力[...] -5` 行）仍由 SOURCE_CHECK 以合成串产出，
  该行由调教循环处理（不在 #74 范围内）。只有损耗条也改为结构化输出后，才能删除 ere 路径的文本网格解析。菜单侧自 #48 起就走 button 记录，与文本路径无关。
- **progress 记录直接使用结构化参数**，无需解析文本。`printProgress` 和 `printMultiColumns` 的 progress 单元转换为：

  ```js
  { kind: 'gauge', key: 条内文字 /* 参数名 */, val: Number(条后数值) }
  ```

  键与值来自参数，`Number` 会忽略用于右对齐的空格（outContent 为空串时归一成
  val=0 而非 NaN。值与黄金侧不符时检查仍会失败，M12 变异证明比对能够检测该差异）。

**percentage 永不进事件流。** 它属于渲染层的算法（原作 10 格字符条
`floor(10×值/下一阈值)` vs 引擎百分比条的取整差异），两侧归一的语义值是
**条后数值**（palam 原值）。`print_palam` 换 printMultiColumns 的 progress
格（#74）后，事件流与原来的文本进度条逐字节一致：首回合比对的基线
（匹配 54 / 版本 10 + 存根 112 + 未解释 0）不动，这正是「换掉表现层不影响
比对」的测试证据。（#212 后基线演进为匹配 57 / 存根 107：体力/气力/
射精（你）三条基础条随 LIFE_BAR/VITAL_BAR/槽条段实现后转为匹配，
progress 格的 (cur/max) 形态由归一化器直接读取——这些结果继续验证了更换显示方式不影响比对。）ere 侧不再生成文本进度条，因此相应的 gauge
正则误判也不再发生；黄金样本侧的解析保持不变（Emuera 只有合成串）。

归一化器的变异测试：M148（val 误读 percentage）/ M149（progress 分支删除）
均由 `test/compare-normalize.test.js` 与首回合比对检测到。

## 范围 B 的三项设计结论（#161 阶段二，判断依据 = 六份录制样本）

### 1. 归一化器：保留七类条目，扩展解析规则

主菜单/存读档/日循环的实际形态（`golden/` 样本实证）与调教段的差异不在
条目类型，在解析形态——**不新增条目类型**，扩展三处（normalize.js）：

- **编号在前的按钮/槽位行**：`[100] 调教`、`[101] 上一页 …`、`[ 5] 备注`
  拆成 menu 条目（调教段 SHOW_USERCOM 的「标签在前」是仅有的例外，其余
  UI 全是编号在前）；`[---]` 占位单元保留为 text（ere 侧使用
  `era.print('[---]')`，与原作对应）。只有整行都符合 `[单元] 标签` 格式时才拆分；否则整行按 text 处理，避免误拆叙述中的编号引用。
- **时间戳归一（验收项）**：存档备注的 `YYYY/MM/DD HH:MM:SS` 前缀替换成
  `<TS>` 占位，黄金侧标签段与 ere 侧 button 正文同一条规则。**归一而非
  忽略**：时间戳的存在与格式仍是断言（缺失时检查失败），只不比较具体值——重录
  时刻必然不同，比较具体值会造成误报失败。
- **富文本标记行**：从 `<shape …><img src='X' …>` 提取 img src，生成 image 条目
  （对应 printImage/printWholeImage 的 names）；纯 shape 丢弃（仅表示排版
  位移）。状态条 `体力[....](cur/max)` 的形态既有 gauge 分支已覆盖，未扩。

### 2. 输出记录范围：遵循 Emuera 的日志保留规则

Emuera 日志保留滚动出屏的历史行，但不保留被 `CLEARLINE` 删除的行。例如，daycycle 样本含三次主菜单输出，标题输入 `0` 的回显和翻页列表的中间结果则会被清除。

ere 夹具的 `lines` 会应用全部 clear 操作。主菜单自 #73 起采用原位置重绘（ADR-0003），若直接比较 `lines`，会把仅因重绘而消失的历史行误报为缺失。因此 `replay-b.js` 使用只追加的 `lines_history`，仅删除与原作 `CLEARLINE` 对应的记录。`ScreenBlock` 重绘和 `set_story_name` 为满足引擎要求而清除的行仍保留在比对流中；两类 clear 通过调用栈区分。

### 3. 输入通道与标记：模拟 Emuera 的输入行为

- 回放使用 `useRule: false` 模拟 Emuera 的自由输入。ere 引擎的 `input()` 默认只接受已显示按钮的快捷键（#129/#130），但回放须允许原作接受的 199、9999 等值，流程错位由输出比对检测。
- 输入标记记录所属 Row。原作清除的回显行（如标题的 0）在夹具中也被删除，未清除的（如读档的 99）保留。`INPUTS` 故事名的回显按 **text** 记录，因为 Emuera 日志无法仅凭文本区分输入回显和叙述。

**比对发现的两个实际缺陷（已处理）**：@SYSTEM_LOADEND 被 #136 误判为死
代码（样本实证引擎在 LOADDATA 后自动调用它输出「兼容性修正中……」——
stub-registry 已勘误，移植按缺陷 issue 处理）；save_game 漏抄原作 `:102` 的
「【保存存档】」前缀（已修复，`saveload-natural-log:90` 为证）。

## era.raw() 的使用限制（变量采集）

raw() 在引擎侧真实存在（app.asar 的 EraApi），但 **SDK 没有声明它**。
将来引擎删掉它时，游戏代码得到的是 `era.raw is not a function` 崩溃，而不是
SDK 的友好提示。本工具链离线运行、直接取夹具 store（内容等价于
`raw().data` 展平）；在引擎里采集时若 raw() 失效，备用方案是 `snapshot_via_get`
（经 era.get 遍历键清单重建快照，实现与测试都在）。引擎升版需复查。
