# 骨架说明：端到端验证后的做法与结论

端到端验证（issue #15）确认玩家能从标题画面进入据点主菜单，并继续操作。本文记录该阶段的架构约定和验证结果，供后续子系统实现时参考；第二节的完成状态是当时的记录，当前进度见 AGENTS.md 和路线图 #101。

**本文只写结构与约定，不写文件路径与代码片段**，以避免文档随重构过期。目录结构、代码约定和引擎限制见 `AGENTS.md`；术语见 `CONTEXT.md`；待办清单见 `docs/stub-registry.md`。

---

## 一、骨架的做法

### 分层按架构角色，不按游戏域

顶层目录按「界面 / 事件 / 系统逻辑 / 变量包装 / 静态数据 / 工具」等架构职责划分；游戏域（调教、迷宫、商店）在二级目录中再分。两个参考项目分别在 1.5 万行和 86 万行规模下采用这一分层；本项目的端到端验证和十七个子系统均按此组织。

口上是唯一的例外：它占原作近一半体量但只有二十来个模块，独立成顶层目录。

### 模块注册有两套机制，语义不同，不要混用

- **事件链**是广播式：一个事件挂多个处理器，**全部执行**，顺序分优先/普通/延后三档，组内取注册的书写顺序。对应原作同名函数的多处定义。
- **分发族**是查表式：一个编号命中**唯一**实现，缺失时返回调用点指定的值。对应原作靠拼接函数名的动态调用。

两者互不依赖，只共用离线索引流程。端到端验证分别覆盖了二者的一个实际用例，证明边界成立。

分发族的核心是**把「已声明的编号空间」与「已实现的编号」分开**：空间内缺失是合法的，空间外是拼写错误、必须抛错。原作的动态调用无法区分这两者，分开是移植的有意增强。**缺失时返回什么由调用点声明**，不由注册表统一规定。原作同一族的四个调用点缺失语义各不相同，硬编码进注册表会在某处悄悄改变游戏行为。

**重复注册必须抛错。** 原作曾发生二十多个函数被同名定义静默遮蔽的事故，玩家侧表现为功能完全失效，原引擎只输出一条警告。本项目要求在启动时抛出异常。

### 运行时不能扫描目录

游戏代码只能用引擎 API 与 `crypto`，没有文件系统。所有清单（口上模块列表、分发族的编号空间）必须显式书写，由离线脚本生成、用标记包裹。离线脚本不受此限，这是「数据自动提取」路线成立的前提。

### 变量一律经包装层读写，不拼字符串

引擎用字符串寻址变量，拼错下标可能不会报错，**缺少静态表却可能使调用直接抛错**。具体行为取决于名字表和数据容器是否存在，与地址的段数无关。包装层提供具名访问器；回归测试从源码提取变量类别，再用引擎代码验证对应表。扫描只能覆盖字面量前缀，动态拼接地址仍需人工检查。

包装层由脚本根据静态数据表生成初稿，再由人工定稿。**生成区与手写区在同一文件内以标记分隔**，重新生成只替换生成区。测试验证此约束；它是后续安全生成大量访问器的前提。

每个变量必须有中文注释说明它在原作中的语义与来源。裸的数字下标不可读，这是全项目最关键的一条约定。

**写变量之前先确认其所属静态表已经实现。** 表不存在时，角色预设会被引擎整行丢弃并逐行记录错误日志；某些寻址族会直接抛错。

### 静态数据是产物，归人工维护

由离线转换器从只读移植源生成，但**纳入版本库**：转换器重跑时默认跳过已有产物，重写必须显式要求。这条规则由测试验证。原型阶段曾因无条件覆盖丢失人工修改。

产物与源之间需要**两类检查**：一类用引擎自己的代码比对（解包引擎程序包并驱动其解析器与装载循环），另一类不经引擎，直接比对转换结果的字节。两者覆盖不同范围：引擎比对只覆盖引擎当前读取的内容；静态表分批实现期间，尚未实现表对应的产物字段不在该检查范围内，须由字节比对覆盖。

### 测试只开一处注入点

全项目唯一的替身注入点，让游戏代码在不启动 GUI 的前提下可测；游戏代码本身零修改、不留任何测试钩子。

**测试注入点是否准确模拟引擎，决定了测试的价值。** 它记录调用，但默认看不见引擎对参数的二次处理和对调用的拒绝。端到端验证期间，三类仅在引擎运行时暴露的缺陷均出自此处：按钮文字被引擎自动添加快捷键前缀；某个寻址族在静态表缺失时抛错；角色因缺少预设数据而未加入。每确认一项引擎行为，就在注入点增加相应记录字段，以便后续断言。

**「我们调用了这个 API」不等于「引擎接受了这次调用」。** 涉及引擎是否接受调用的断言，要么使用引擎代码验证，要么让注入点准确模拟引擎的条件检查。

### 追溯靠文件头注释，不靠目录镜像

每个移植文件在头部注明来自原作的哪个文件与哪个函数，精确到函数级。这比目录镜像更准，且不受重构影响。

有意偏离原作的地方（如把「编号越界」的判据从序号语义改写为 ID 语义）必须在注释里写明依据，否则后来者会以为是移植错误而「改回去」。

### 存根是有记录的待办项，不是遗漏

已接入但未实现的调用点，运行时输出一行带原作函数名的占位；同时登记进一份**可检索的清单**，注明源文件行号与归属子系统。测试核对清单与代码；漏登记时检查失败。

后续实现按此清单分配：找到对应条目，将占位实现替换为实际实现，再从清单中删除该条目。

## 二、十二项决策的验证结论

端到端验证要回答的不是「标题画面能否显示」，而是「十二项决策能否共同工作」。逐条结论如下。

| 决策 | 主题                     | 结论                                       |
| ---- | ------------------------ | ------------------------------------------ |
| #2   | 引擎脚手架               | **成立**，且已被后续每一次启动反复验证     |
| #3   | 同名函数多定义的生效规则 | **部分被推翻**，见下                       |
| #4   | 参考项目的移植手法       | **成立**，分层与包装层形状据此实现         |
| #5   | 变量模型映射             | **成立**，含内置标量并入旗标表的保留区安排 |
| #6   | 事件机制与转场           | **成立，且首次在运行时被验证**，见下       |
| #7   | 动态函数分发             | **成立**，接口形状按原决策实现             |
| #8   | 口上载体                 | **尚未验证**，端到端流程不包含口上         |
| #9   | 输出比对工具链           | **尚未验证**，只做了单点断言，未做逐字比对 |
| #10  | 数据自动提取管线         | **成立**，产物边界规则经多次变异检验       |
| #11  | 目录分层与命名           | **成立**，实施中扩充了角色域这一层         |
| #12  | 两份同名标题函数的仲裁   | **成立**，移植以生效的那份为准             |
| #13  | 变量模型的三条未证实行为 | **成立但需细化**，见下                     |

### #3：第 6 节被 #6 推翻

原判断是「事件链中任一函数发起转场，整条链立即中止」。这是错的：准确语义是暂存目标、链继续跑完、最后一个生效。#6 已用原作运行日志与 Emuera 实现双重确认并在 #3 留下勘误。

按旧理解实现会静默跳过五百余行回合结算，玩家通常到中期才会发现数值异常。端到端验证的实现工作专门为此编写了变异测试：**注入旧理解会使相关测试失败**。

### #6：首次在运行时被验证

#6 推翻 #3 时给出的是文档层面的论证。端到端验证将其变成可执行断言：「发出转场后剩余处理器仍全部执行」「多次转场最后一个生效」「捕获异常的代码吞掉转场信号则测试失败」三条都有用例，且变异测试证明这些用例能检测相应失效。

那条硬约束（任何捕获异常的地方必须先原样重抛转场信号）值得单独强调：它会在后续十七个子系统里反复出现，是最容易被后来者破坏的一条。

### #11：扩充了角色域

分层本身成立。实施中新增了一个角色域的顶层位置，安放角色专属初始化这类既非界面也非系统逻辑的代码，并相应扩了导入分组顺序。这是**补充而非修正**，已在 #11 留言。

### #13：结论成立，但「未声明序号」的行为不统一

#13 在一维旗标表上实测得出「读未声明序号返回 undefined、写入静默创建并存进存档」。这条在其测量范围内完全正确，因此包装层需要为未声明值提供默认值。

但端到端验证及其后的调教流程观察到其他行为：角色未加入时，二维表写入会因条件检查而被忽略，**静默丢弃而不创建**；静态表缺失时则**直接抛错**。第二次出现该问题时（调教域缺五张表）才确认判定条件：不是「寻址形态」，而是**名字表与数据容器是否存在**的组合。两次均已在 #13 补充勘误。

**对后续子系统的意义**：不要将一种寻址形态的实测结果推广到另一种。写变量前确认所属静态表已经实现，这一步先于为未声明值提供默认值。

### #8 与 #9 为何仍未验证

端到端流程不包含口上，也没有需要逐字比对的输出，这是选择该流程时已知的范围限制。两者须待第一个口上模块和第一个可比对的子系统实现后才能验证。

**这不是遗漏，而是端到端验证的范围限制。** 后续实现涉及这些部分时，应将「决策是否成立」作为明确的验收项。

## 三、只有在引擎里实际运行才暴露的三类缺陷

端到端验证期间有三类缺陷在测试全部通过后，才在引擎实际运行时发现。它们都源于同一个测试注入点：**测试证明了「我们调用了引擎」，没有证明「引擎接受并按预期处理了这次调用」**。

1. **未模拟输出参数的处理**：引擎自动添加快捷键前缀，与按钮正文中手写的前缀重复。
2. **未检查变量访问的前置条件**：某类变量因静态表缺失而抛错，测试夹具却接受了写入。
3. **未检查引擎的拒绝条件**：缺少角色预设时，引擎未加入角色，但夹具仍记录了调用，两轮验收均未发现。

这三类问题都需要先读取引擎代码确认行为，再补充测试夹具的记录和断言。

**后续实现的通则**：接入一个引擎 API 前，先阅读其实现，再决定测试写法。

## 四、验收「此行为有测试」时必须执行变异测试

端到端验证期间发现三条**无效用例**：用例名声称覆盖某个行为，实际上无法检测该行为失效。

- 一条断言在「行为正确」与「行为被删掉」两种情况下结果相同；
- 一条记录了失效方式，但它是表征测试，被测代码如何修改都通过；
- 一条的被测条件两个分支在测试数据中恰好重合，断言无法区分。

三条的共同特征是：**测试构造的环境中，被测条件的两个分支没有被区分**。仅阅读用例名和断言无法发现这一点，必须改变被测行为并确认相关测试失败。

因此，需求记录中凡写着「此行为有测试」的验收项，验收时必须逐条做变异测试。这已纳入工作分配流程。
