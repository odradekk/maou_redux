# 骨架说明：曳光弹跑通后的做法与结论

曳光弹（issue #15）已全程跑通：玩家能从标题画面走到据点主菜单，并在其上持续操作。这份文档记录**这条路径证明了什么**，好让后续十七个子系统照着长，不必各自重新发明结构。

**本文只写结构与约定，不写文件路径与代码片段**——那些会失效。具体落点见 `AGENTS.md`（目录结构、代码约定、引擎硬约束），术语见 `CONTEXT.md`，欠账见 `docs/stub-registry.md`。

---

## 一、骨架的做法

### 分层按架构角色，不按游戏域

顶层目录是「界面 / 事件 / 系统逻辑 / 变量包装 / 静态数据 / 工具」这样的角色划分，游戏域（调教、迷宫、商店）在二级目录里再分。两个参考项目在 1.5 万行与 86 万行两个量级上都守住了这个分层，本项目从曳光弹到十七个子系统都照此办理。

口上是唯一的例外：它占原作近一半体量但只有二十来个模块，独立成顶层目录。

### 模块注册有两套机制，语义不同，不要混用

- **事件链**是广播式：一个事件挂多个处理器，**全部执行**，顺序分优先/普通/延后三档，组内取注册的书写顺序。对应原作同名函数的多处定义。
- **分发族**是查表式：一个编号命中**唯一**实现，缺失时返回调用点指定的值。对应原作靠拼接函数名的动态调用。

两者互不依赖，只共用离线索引管线。曳光弹里各有一个真实用例跑通，边界成立。

分发族的核心是**把「已声明的编号空间」与「已实现的编号」分开**：空间内缺失是合法的，空间外是拼写错误、必须抛错。原作的动态调用无法区分这两者，分开是移植的有意增强。**缺失时返回什么由调用点声明**，不由注册表统一规定——原作同一族的四个调用点缺失语义各不相同，硬编码进注册表会在某处悄悄改变游戏行为。

**重复注册必须抛错。** 原作有真实事故：二十多个函数被同名定义悄悄遮蔽，玩家侧表现为功能完全失效，而原引擎只给一条警告。本项目要它在启动时就炸出来。

### 运行时不能扫描目录

游戏代码只能用引擎 API 与 `crypto`，没有文件系统。所有清单（口上模块列表、分发族的编号空间）必须显式书写，由离线脚本生成、用标记包裹。离线脚本不受此限，这是「数据自动提取」路线成立的前提。

### 变量一律经包装层读写，不拼字符串

引擎用字符串寻址变量，拼错下标不会报错——**而缺一张静态表会让同一句话直接抛错**。行为由「名字表在不在」与「该角色的数据桶在不在」的组合决定，与寻址写成几段无关。包装层是第一道防线：具名访问器让拼写错误变成一眼可见的调用错误；第二道是一条从源码扫出全部寻址族、再用引擎自己的代码逐个探的回归锁。

包装层由脚本从静态数据表生成初稿、人工定稿，**生成区与手写区在同一文件内以标记分隔**，重新生成只替换生成区。这条约束有测试守着——它是后续上万行访问器能否安全生成的前提。

每个变量必须有中文注释说明它在原作中的语义与来源。裸的数字下标不可读，这是全项目最关键的一条约定。

**写变量之前先确认它所属的静态表已经落地。** 表不在时，角色预设会被引擎整行丢弃并逐行记错误日志；某些寻址族则直接抛错。

### 静态数据是产物，归人工维护

由离线转换器从只读移植源生成，但**进版本库**：转换器重跑默认跳过已存在的产物，重写必须显式要求。这条规则有测试钉死——原型阶段曾因一句无条件覆盖销毁人工修改。

产物与源之间要有**两层守护**：一层用引擎自己的代码对拍（解包引擎程序包、驱动它的解析器与装载循环），一层不经引擎、直接比对转换结果的字节。两层不是冗余——引擎对拍只覆盖「引擎当前看得见的东西」，静态表分批落地时，未落地表对应的产物字段处在无人看守的窗口期，只有字节守护能补位。

### 测试只开一处缝

全项目唯一的替身注入点，让游戏代码在不启动 GUI 的前提下可测；游戏代码本身零修改、不留任何测试钩子。

**这道缝的保真度决定了测试的价值。** 它记录调用，但引擎对参数的二次加工、对调用的拒绝，缝里默认看不见——曳光弹期间三次实机缺陷全部出自这个位置：按钮文字被引擎自动加了前缀、某个寻址族在静态表缺失时抛错、角色因缺预设数据而根本没被加入。每查明一处引擎行为，就把它补进缝的记录字段，让它此后可断言。

**「我们调了这个 API」不等于「引擎接受了这次调用」。** 涉及引擎是否接受的断言，要么用引擎自己的代码验证，要么让缝如实镜像引擎的守卫。

### 追溯靠文件头注释，不靠目录镜像

每个移植文件在头部注明来自原作的哪个文件与哪个函数，精确到函数级。这比目录镜像更准，且不受重构影响。

有意偏离原作的地方（如把「编号越界」的判据从序号语义改写为 ID 语义）必须在注释里写明依据，否则后来者会以为是移植错误而「改回去」。

### 存根是有记录的欠账，不是遗漏

已接线但未实现的调用点，运行时打一行带原作函数名的占位；同时登记进一份**可检索的清单**，注明源文件行号与归属子系统。清单与代码之间有测试对账——漏登记会红。

后续票据此认领工作：找到清单里的一行，把对应的壳换成真实实现，然后销账。

## 二、十二个决议的验证结论

曳光弹要回答的不是「标题画面能不能显示」，而是「十二个决议能不能拼在一起」。逐条结论如下。

| 决议 | 主题                     | 结论                                           |
| ---- | ------------------------ | ---------------------------------------------- |
| #2   | 引擎脚手架               | **成立**，且已被后续每一次启动反复验证         |
| #3   | 同名函数多定义的生效规则 | **部分被推翻**，见下                           |
| #4   | 参考项目的移植手法       | **成立**，分层与包装层形状照它落地             |
| #5   | 变量模型映射             | **成立**，含内置标量并入旗标表的保留区安排     |
| #6   | 事件机制与转场           | **成立，且首次在运行时被验证**，见下           |
| #7   | 动态函数分发             | **成立**，接口形状原样落地                     |
| #8   | 口上载体                 | **尚未验证**——曳光弹路径上没有口上             |
| #9   | 输出对拍工具链           | **尚未验证**——曳光弹只做单点断言，未做逐字对拍 |
| #10  | 数据自动提取管线         | **成立**，产物边界规则经多次变异检验           |
| #11  | 目录分层与命名           | **成立**，实施中扩充了角色域这一层             |
| #12  | 两份同名标题函数的仲裁   | **成立**，移植以生效的那份为准                 |
| #13  | 变量模型的三条未证实行为 | **成立但需细化**，见下                         |

### #3：第 6 节被 #6 推翻

原判断是「事件链中任一函数发起转场，整条链当场中止」。这是错的——准确语义是暂存目标、链继续跑完、最后一个胜出。#6 已用原作运行日志与 Emuera 实现双重确认并在 #3 留下勘误。

按旧理解实现会静默跳过五百余行回合结算，是玩到中期才发现数值不对的那类缺陷。曳光弹的实现票专门为此做了变异测试：**注入旧理解会让测试当场变红**。

### #6：首次在运行时被验证

#6 推翻 #3 时给出的是文档级论证。曳光弹把它变成了可执行的断言——「发出转场后剩余处理器仍全部执行」「多次转场最后一个生效」「捕获异常的代码吞掉转场信号则测试失败」三条都有用例，且都被变异测试证明确实在守。

那条硬约束（任何捕获异常的地方必须先原样重抛转场信号）值得单独强调：它会在后续十七个子系统里反复出现，是最容易被后来者破坏的一条。

### #11：扩充了角色域

分层本身成立。实施中新增了一个角色域的顶层位置，安放角色专属初始化这类既非界面也非系统逻辑的代码，并相应扩了导入分组顺序。这是**补充而非修正**，已在 #11 留言。

### #13：结论成立，但「未声明序号」的行为不统一

#13 在一维旗标表上实测得出「读未声明序号返回 undefined、写入静默创建并存进存档」。这条在它测量的范围内完全正确，包装层的兜底也因此是必需的。

但曳光弹与其后的调教路径撞到了别的行为：角色未加入时二维表的写入被守卫拦下、**静默丢弃而不创建**；静态表缺失时**直接抛错**。第二次撞见（调教域缺五张表）才看清判据——不是「寻址形态」，是**名字表与数据桶各自在不在**的组合。两次都已在 #13 补勘误。

**对后续子系统的意义**：不要从一种寻址形态的实测结果推广到另一种。写变量前确认所属静态表已落地，这是比包装层兜底更靠前的一道防线。

### #8 与 #9 为何仍未验证

曳光弹的路径上没有口上，也没有需要逐字对拍的输出——这是选择这条路径时就预见到的。两者要等第一个口上模块与第一个可对拍的子系统落地时才谈得上验证。

**这不是遗漏，是曳光弹的边界。** 后续票在触及它们时，应当把「决议是否站得住」当作该票的显式验收项之一。

## 三、实机才暴露的三类缺陷

曳光弹期间有三次缺陷是测试全绿、实机才发现的，全部出自同一条缝：**测试证明了「我们调用了引擎」，没有证明「引擎接受并按预期处理了这次调用」**。

1. **引擎对输出参数的二次加工看不见**——按钮文字被引擎自动加了快捷键前缀，与移植时手写的前缀重复。
2. **引擎对变量寻址的前置依赖看不见**——某一族寻址在其静态表缺失时抛错，而同一份代码里其他族的写入都静默通过。
3. **引擎对调用的拒绝看不见**——角色因缺少预设数据而根本没被加入，调用记录却完好无损，两轮验收都被放过。

三次的修法相同：查明引擎的真实行为（解包程序包读它自己的代码），把该行为补进测试缝，让它此后可断言。

**给后续票的通则**：新接一个引擎 API 时，先看它的实现，再决定测试怎么写。

## 四、验收「此行为有测试」的唯一手段是变异测试

曳光弹期间抓到三条**空用例**——用例名声称守住某个行为，实际上守不住：

- 一条断言在「行为正确」与「行为被删掉」两种情况下结果相同；
- 一条把失效方式记录了下来，但它是表征测试，production 代码怎么改它都绿；
- 一条的被测条件两个分支在测试构造的世界里恰好重合，断言无法区分。

三条的共同特征是：**测试世界里，被测条件的两个分支没有分开过**。光读用例名与断言看不出来，只有把被测行为改坏、看测试是否变红才能发现。

因此工单里凡写着「此行为有测试」的验收项，验收时必须逐条做变异测试。这条已经进了工单派发的标准流程。
