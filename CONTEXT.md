# CONTEXT

《ERA魔王 年度版》移植项目的术语表。

本项目需要对应日文原作、简体中文汉化和 EraElectron API 三套名称。例如，原作的 `素質` 在汉化中称为「素质」，在引擎中对应 `talent`。本表记录这些对应关系，供命名和编写文档时查阅。

命名（标识符、测试名、issue 标题、提交信息）时使用本表的「本项目用词」一列。表中没有的概念，应确认是否应使用已有用词；确有新增概念时，再补充本表。

## 记法约定

- 原作的变量与函数按 Emuera 原样大写书写：`FLAG:36`、`@EVENTFIRST`。
- 引擎 API 与寻址字符串保持引擎规定的大小写：`era.printButton`、`flag:36`。
- 两者对照时先写原作、后写引擎：`GLOBAL:99` ↔ `global:99`。

## 写作约定

文档、注释、测试名和 issue 一律使用常用工程术语，避免行业外比喻、网络用语和临时造词。下表列出应避免的表达及其按语义可选的替代说法；写作时应根据上下文选择准确的词，不作机械替换。

| 不用                                 | 改用                                                   |
| ------------------------------------ | ------------------------------------------------------ |
| 台账、对账、在账、销账、欠账、收账   | 条目表、清单、核对、待办项                             |
| 口径                                 | 判定标准、统计方式、版本                               |
| 留痕、定档、存量、发霉               | 记录、定稿、现有、过期失效                             |
| 点名、靶向、门控、守门、网住         | 报出位置、指向、需要引擎、阻止                         |
| 钉死、接线                           | 用回归测试固定、接入                                   |
| 假绿、硬崩、硬红                     | 误报通过、直接崩溃、直接判失败                         |
| 档（快档／全量档）、硬口径、弱路径   | 模式、严格标准、宽松判定                               |
| 三件套、换皮、铺开、一键、复跑、两相 | 三项自检、替换表现层、推广到、一条命令、重跑、两个阶段 |
| 曳光弹、测试缝、对拍                 | 端到端验证、测试注入点、输出比对                       |

「门面」「存根」「归一化」「状态机」「测试夹具」是标准领域术语，可以保留；首次出现时应说明其在本文中的具体含义。其他词按实际行为表述，例如写清默认处理或回退条件，不用泛化的「兜底」。

**`callname` 的两个负数下标**：`addCharacter` 将角色预设的**名前**写入 `callname:id:-1`，将**呼び名**写入 `callname:id:-2`；缺少呼び名时使用名前。`callname:c:u` 表示 c 对 u 的称呼，未设置时使用 u 的 `-2`。多数预设中两个值相同，测试应使用不同值来验证下标，避免将两者写反而未被发现（#44/#50）。原作将 `SAVESTR:x` 赋为 `%NAME:x%`，因此它对应名前。

**`FLAG` 的保留区**：Emuera 有几个内置标量（日期、时段、持有金、角色指针）在引擎里没有对应表，按决策并入 `flag`，占用一段高位序号。它们在本项目里仍用各自的中文名（日期、所持金…），不叫「旗标」。

## 流程与机制

| 本项目用词 | 原作                         | 引擎              | 说明                                                                                                                                 |
| ---------- | ---------------------------- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 转场       | `BEGIN`                      | 无对应，移植自建  | 切换游戏阶段。**不是立即跳转**，详见下                                                                                               |
| 转场信号   | —                            | 移植自建          | `BEGIN` 的 JS 载体，用异常实现「结束当前函数」                                                                                       |
| 游戏状态   | `BEGIN` 的目标关键字         | 移植自建          | 标题、新游戏、据点、调教、调教后、回合结束                                                                                           |
| 事件链     | 同名函数的多处定义           | 移植自建          | 一个事件挂多个处理器，全部执行，分三档优先级                                                                                         |
| 分发族     | `TRYCALLFORM` 的同前缀函数群 | 移植自建          | 按编号命中唯一实现的查表机制                                                                                                         |
| 口上       | `口上` / `EVENT_K*`          | —                 | 角色台词与反应的状态机，占原作近一半体量                                                                                             |
| 调教       | `調教`                       | —                 | 核心玩法循环                                                                                                                         |
| 据点       | `SHOP`                       | —                 | 主菜单所在的枢纽画面。原作函数名叫 shop，但它不是商店                                                                                |
| 回合结束   | `TURNEND`                    | —                 | 日期推进与结算                                                                                                                       |
| 出售       | `售卻` / `SELL_*`            | —                 | 把奴隶、母乳、影像、决斗金换成资金。菜单文本是「贩卖奴隶」；日文的「売却」不用                                                       |
| 成熟度演出 | `SELL_MATURO_K*`             | —                 | 出售奴隶时按买家类型分支的长段演出                                                                                                   |
| 处刑       | `處刑` / `EXECUTION`         | —                 | 处置角色的一组结局向流程（放逐、公开处刑、苗床等）                                                                                   |
| 家族       | `關係設置` / `RELATION_*`    | —                 | 角色之间的血缘与姻亲关系。汉化用「家族」，**不用「亲属」**（后者在语料里零出现）                                                     |
| 恋人       | `LOVERS`                     | —                 | 角色与魔王之外对象结成的伴侣关系，城镇线的一支                                                                                       |
| 结婚日     | `MARRIAGE_DAY`               | —                 | 角色与怪物按种族分支的配对流程                                                                                                       |

| 妊娠       | `NINSIN`                     | —                 | 受孕、孕期推进与生产                                                                                                                 |
| 育儿       | `CHILD_CARE_*`               | —                 | 生产之后的抚育流程，与妊娠同一文件但不是同一件事                                                                                     |

| 待办清单        | 存根与未实现变量赋值的可检索清单，后续工作据此分配                                                                                                                                    |
| 追溯注释        | 文件头标注该文件移植自原作的哪个文件与哪个函数                                                                                                                                        |
| 测试注入点      | 全项目唯一的替身注入位置，让游戏代码在不启动 GUI 的前提下可测                                                                                                                         |
| 引擎比对        | 解包引擎程序包并直接驱动其代码验证产物，避免自行实现行为副本                                                                                                                          |
| 注册名          | 资源在 `res/` 注册表 csv 里的调用名，引擎装载与查名两侧统一小写；BGM 的注册名沿用原作 `PLAYBGM` 的实参（文件名本身）                                                                  |
| 变异测试        | 故意改变被测行为，确认相关用例会失败。验收「此行为有测试」时必须执行此检查                                                                                                            |

## 架构术语

决策见 `docs/adr/`。这些词是移植版自建的，原作与引擎都没有对应物。

| 用词         | 含义                                                                                                                                                                                                                                                                                                                                   |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 域           | 玩法维度的所有权单元：口上 / 调教 / 角色 / 据点 / 迷宫 / 侵略 / 事件 / 系统。一个域拥有若干变量区段；清单是产物里的一张表，不是硬编码枚举                                                                                                                                                                                              |
| 门面         | 变量访问的入口，按域分组，并为一维和二维变量提供对称访问方式：`chara(cid).<域>.<字段>` 与 `game.<域>.<字段>`。使用生成的 class，不使用 Proxy；字段名用中文（与 ERB 对应）；`chara(cid)` 按角色 ID 缓存单例视图。既有扁平 `era_flag` / `era_global` 并存；既有一维变量不强制迁移，口上域两个样本（#71）已迁，其余按对应子系统的计划处理 |
| 区段所有权   | 「某段变量下标归某个域」的映射。由离线脚本从 `target/` 实测导出，非人工划定                                                                                                                                                                                                                                                            |
| 无域状态模块 | 几乎不写持久状态、被多个域共用的文件。区段所有权判据对它**不适用**，因此不归入任何玩法域，归入无域状态模块，见 ADR-0007。首例 `EQUIP.ERB`。与之相对，`FUNC_CLOTH.ERB` 有 50 处持久写入，判据成立                                                                                                                                       |
| 跨域写       | 一个域写入另一个域拥有的区段。允许，但必须经属主域导出的具名方法；**跨域读不受限**                                                                                                                                                                                                                                                     |
| 画面组件     | 表现层的单元，知道自己占几行（绘制前后 `getLineCount()` 的差值）                                                                                                                                                                                                                                                                       |
| 重绘         | 组件清掉自己占的行并重画（`clear(自己的行数)` + 重画）。**只发生在玩家交互之后**：叙述流中间重绘会打断玩家的右键快进                                                                                                                                                                                                                   |
| 两个阶段     | 每个 issue 内部的两步：先 1:1 移植（通过输出比对与测试），再重构进目标架构；这不是项目级的阶段顺序                                                                                                                                                                                                                                     |
| 引擎事实     | 引擎对参数执行的一次变换，且**测试夹具的记录行为依赖它**（如 `barWidth` 缺省 24 会让条后文字整列不渲染）。将该事实写入表中，同时供锚点校核（检查引擎是否变化）与调用点规则（检查调用是否满足条件）使用；两者都不使用的内容属于背景说明，不算引擎事实。可达性分三层，见 ADR-0005                                                        |

**「行（Row）」是引擎的编程行，不是显示行。** 一次 `printMultiColumns` 无论输出几个格子都只占一个 Row，`clear(1)` 会把它们一起清除；而一段长文本自然换行成三个显示行时仍只是一个 Row。画面组件的行数指的是 Row 数。

## 输出 API 与原作的对应

**`PRINTC` / `PRINTLC` 不是居中打印，也不换行。** 按 Emuera 官方文档（PRINTC 系）：两者都把文本补到配置「PRINTCの文字数」（初始值 25）指定的宽度再打印；`C` 是右对齐（左侧补半角空格），`LC` 是左对齐。**只有同一行排满「PRINTCを並べる数」（初始值 3，`PRINTCPERLINE()`）个项目时才自动换行**；名字里的 `L` 表示左对齐，不表示换行（换行仍由 `PRINTL` 负责——后缀表的 `K` 是 `FORCEKANA`、`D` 是忽略 `SETCOLOR`，所以 `PRINTLCD` 是「左对齐补位 + 默认色」）。

**引擎的 `printButton` 自成一行，等价于原作的一个 `PRINTLC`（或 `PRINTBUTTON`）加上结束那一行的 `PRINTL`。** 由此两条推论：

- 原作「若干 `PRINTLC` 串 + 一个收尾的 `PRINTL`」在 ere 侧只需要按钮，**不再补空行**；只有原作另写的独立 `PRINTL`（真正的空行）才译成 `era.println()` / `era.print('')`。多补一条就是多出来的空行（#562）。
- 原作一行里排多个 `PRINTLC`（中间没有 `PRINTL`）时，ere 侧按按钮平铺逐行渲染，这是**记名差异**（排版），不为此改引擎用法。

技能指南（`.agents/skills/emuera-basic-agent-guide/`，逐字同步的外部材料）把 `PRINTC` / `PRINTLC` 写成「居中打印」且「`PRINTLC` 还会换行」，与引擎行为不符；不改本地副本，一律以本节为准。

## 三条容易误解的语义

**转场不是立即跳转。** 发出转场后，当前函数立刻结束，但事件链**继续跑完剩余的处理器**；期间若再次发出，后者覆盖前者，最后一个生效；整条链退出后才真正切换状态。按「立即跳转」实现会静默跳过大段结算逻辑。

**写入未声明序号的行为，取决于名字表和数据容器是否存在。** 名字表指 `yml/` 中的静态表，数据容器指引擎保存该类变量值的 `data` 对象。两者都存在时，未声明下标按数字处理并成功写入；只有名字表时，写入被静默丢弃；**只有数据容器时，写入直接抛错**。两段和三段地址都遵循此规则。确认一种变量能写入，不能证明其他变量也具备所需的表和数据容器。

**「已加入序号」与「角色 ID」在原作里常常重合，但不等价。** 原作按加入顺序连续编号，故两者在原作语境下可互换；ere 侧一律用角色 ID，因此原作里形如「编号大于总数即越界」的判据不能照抄，须按语义改写为「不在已加入列表中」。
